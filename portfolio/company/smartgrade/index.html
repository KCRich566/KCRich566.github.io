SMARTGrade Auto-Grading System

Context

SMARTGrade inspection machines produce structured inspection results for manufactured parts. The difficult part begins after inspection: every customer can define different acceptance rules, severity levels, and reporting needs.

This project focused on an Auto-Grading system that receives inspection data, applies a customer-configured inspection standard, and presents a clear result for operators and engineers.

The problem

A machine can identify defects, but a defect list is not automatically a production decision. The same observation may be acceptable for one product revision and rejected for another. Rules also need to remain traceable when a customer updates a standard.

The system therefore needed to separate three concerns:

  1. Raw inspection observations from SMARTGrade.
  2. Versioned customer inspection criteria.
  3. The final grading decision and its explanation.

Solution flow

SMARTGrade inspection machine
            |
            v
     Result ingestion
            |
            v
  Normalization and validation
            |
            +------> Raw result archive
            |
            v
 Customer standard and revision
            |
            v
       Rule evaluation
            |
            v
   Grade + reason + evidence
            |
            v
 Operator UI / reports / export

Each grading result keeps the criteria revision used for evaluation. This makes a result explainable instead of presenting a score with no context.

Designed behavior

The ingestion boundary validates identifiers, timestamps, measurement units, defect types, and machine status before a result enters the grading pipeline. Invalid data is kept as a visible processing error rather than silently discarded.

The rule engine evaluates inspection items in a deterministic order. It produces both a summary grade and item-level evidence: which rule matched, which measurement was compared, and why the item passed or failed.

The UI emphasizes the production question first: pass, review, or fail. Engineers can expand the result to inspect defect locations, measurements, rule thresholds, and the original machine payload.

Engineering challenges

Different customer standards

Customer configuration is modeled as data rather than hard-coded branches. A standard has a version, scope, thresholds, severity mapping, and effective time. New revisions can be tested before activation.

Reliable handoff

The ingestion flow is idempotent by inspection identity. Retrying a machine transmission does not create a second grading decision. Processing states make incomplete or delayed results visible to operators.

Explainability

A grading decision is stored with its inputs and rule revision. This supports troubleshooting, customer review, and later analysis without requiring the system to reconstruct historical configuration.

Outcome

The system provides a repeatable path from machine inspection data to an operational decision. It reduces manual interpretation, makes customer-specific standards manageable, and gives engineers evidence when a result needs investigation.

Company-specific implementation details are intentionally generalized in this case study.
