KCRich566 Portfolio Website

設計目的

這個網站不是單純把履歷放到網路上的展示頁，而是一個用來整理專業經驗、作品案例、技術筆記與實驗成果的長期平台。網站主要面向客戶、招聘主管，以及未來需要回顧自己工作脈絡的我。因此設計的重點不是一次性的視覺宣傳，而是讓訪客可以快速理解我的能力，也讓內容可以隨著經驗累積持續增加。

網站的內容分成 Portfolio、Notes、Lab 與 About 四個方向。Portfolio 是最主要的區域，負責呈現曾經參與的專案、公司經驗與個人作品，並且以案例研究的方式說明背景、問題、負責範圍、技術選擇與結果。Notes 用來保存系統設計、軟體工程、開發工具與學習過程中的技術內容。Lab 則保留實驗性質較高的作品與想法，About 用來補充個人背景、能力、經歷與聯絡資訊。首頁不重複完整內容，而是負責把訪客引導到這幾個主要入口，並且優先呈現精選作品、最新筆記與實驗內容。

這樣的設計讓網站同時具備作品集與個人知識庫的性質。Portfolio 回答「我做過什麼，以及我如何解決問題」，Notes 回答「我如何理解與整理技術」，Lab 則回答「我正在嘗試什麼」。三者互相支援，使網站不會只剩下職稱與技術名稱，也能呈現實際工作的思考過程。

技術選擇

網站使用 Next.js 作為應用程式框架，使用 TypeScript 讓頁面、資料結構與元件之間的契約更清楚，並使用 Tailwind CSS 與現有的全域樣式完成介面。Next.js 採用 App Router，因此頁面路由直接對應到 app 目錄中的檔案。首頁、About、Portfolio、Notes 與 Lab 各自有清楚的入口，分類與文章則由動態路由處理。

內容本身保留在 myArticles 目錄中，而不是直接寫死在 React 元件裡。Portfolio 可以使用 Markdown 或 MDX，Notes 也可以使用 Markdown 或 MDX。這個安排把「內容」與「呈現內容的程式」分開，使新增一篇文章時不需要修改頁面元件，也讓文章可以在版本控制中以一般文字檔案被審查、比較與維護。

網站選擇靜態輸出，而不是在正式環境啟動一個長時間執行的 Next.js 伺服器。next.config.ts 將 output 設為 export，並開啟 trailingSlash，讓建置結果可以直接由 GitHub Pages 提供服務。由於靜態網站沒有 Next.js Image Server 可以在部署後處理圖片，圖片最佳化也設定為 unoptimized。這些設定反映了部署目標：網站需要的是可靠、簡單且成本低的靜態託管，而不是伺服器端執行環境。

內容資料流

在建置階段，lib/portfolio.ts 與 lib/notes.ts 會從檔案系統讀取文章。程式先依照目錄取得分類，再讀取符合 .md 或 .mdx 副檔名的檔案。文章開頭的 frontmatter 會透過 gray-matter 解析成標題、描述、日期、標籤、公司、狀態與精選狀態等資料，文章剩餘的部分則保留為 Markdown 或 MDX 內容。

Portfolio 的資料讀取器會遞迴搜尋分類底下的檔案，因此作品可以依照公司、個人作品或其他未來需要的分類存放。Notes 目前以分類目錄直接對應網址中的 category。兩種內容都會在讀取時整理成明確的 TypeScript 資料型別，頁面元件不需要知道檔案系統的細節，只需要使用作品或筆記資料。

文章標題會先透過 unified 與 remark parser 解析，再使用 github-slugger 產生標題識別碼。這些標題資料會提供給文章旁的目錄元件，讓長篇內容仍然可以快速跳轉。真正輸出文章時，Portfolio 與 Notes 頁面使用 next-mdx-remote 在建置期間編譯 MDX，並透過 rehype-slug 為標題加入可連結的識別碼。Notes 另外使用 rehype-pretty-code 處理程式碼區塊，並將連續的不同語言程式碼區塊整理成可切換的 code tabs，讓同一段概念在不同語言中的實作可以並列閱讀。

頁面與路由設計

首頁由 Hero、網站定位、精選 Portfolio、Featured Lab 與最新 Notes 組成。它的責任是建立第一印象並提供內容入口，因此不在首頁塞入所有文章，而是將內容摘要與導覽集中在適合的位置。Header 與 Footer 放在根 layout 中，讓所有頁面共享一致的網站框架。

Portfolio 索引頁會取得所有作品並交給 PortfolioIndex 呈現。作品詳細頁使用 /portfolio/[category]/[slug] 路由，根據 category 與 slug 找到對應檔案，再將內容交給 PortfolioDetail。Notes 採用相同的概念，索引頁負責瀏覽與分類，詳細頁使用 /notes/[category]/[slug] 路由載入單篇筆記。這種路由設計讓網址本身具有語意，也使不同分類的內容可以在未來持續擴充。

動態路由並不是等到使用者請求時才讀取檔案。Portfolio 與 Notes 的詳細頁都實作 generateStaticParams，在建置期間先列出所有已知的 category 與 slug。Next.js 便可以為每一篇內容產生實體 HTML，正式部署時不需要查詢資料庫，也不需要 Node.js runtime。文章不存在時仍會透過 notFound 交給 Next.js 處理，避免把錯誤內容當成正常頁面輸出。

為什麼採用內容檔案而不是資料庫

目前網站的主要需求是展示與累積個人內容，而不是讓訪客在線上編輯資料。使用 Markdown 與 MDX 檔案可以讓每一次內容變更都和程式碼一樣經過 Git 版本控制，也可以在 pull request 中檢查文字、frontmatter 與程式碼範例。對個人作品集而言，這比引入資料庫、後台登入與內容管理服務更符合實際需求。

這個選擇也讓本機開發流程保持簡單。完成 npm install 後，可以透過 npm run dev 啟動開發伺服器，新增或修改文章後直接重新整理頁面即可看到結果。當內容結構仍然由檔案與型別約束時，未來若需要更換部署平台，也只需要保留建置結果或調整部署流程，不必搬遷一套線上資料庫。

CI/CD 設計

CI/CD 的核心目標是把內容檢查、網站建置與正式發佈分開。所有 pull request 都會啟動 GitHub Actions 的 build job。工作流程先從目前的 repository checkout 原始碼，接著使用 MYARTICLES_TOKEN 初始化私有的 myArticles submodule。這一步很重要，因為網站的內容來源和網站程式碼可以分開管理，而建置仍然需要在 CI 環境取得正確版本的內容。

工作流程在 Ubuntu runner 上使用 Node.js 22，並啟用 npm cache。依賴安裝完成後，CI 會執行 npm run lint 檢查程式碼品質，再執行 npm run build 產生靜態網站。只要 pull request 或 main 分支的 push 無法通過 lint 或 build，這次變更就不應該被視為可部署版本。這個階段只驗證來源程式碼與內容能否正確產出網站，不會修改正式的 Pages repository。

正式發佈則由 tag push 觸發。tag push 會先執行與其他 CI 事件相同的 checkout、依賴安裝、lint 與 build，因此只有通過相同驗證的版本才會進入發佈階段。建置完成後，工作流程把 out 目錄上傳成 artifact，接著使用 GithubPages_Publisher 憑證 checkout KCRich566/KCRich566.github.io 的 main 分支。

發佈步驟會保留 Pages repository 的 .git 與 .github，清除其他舊網站檔案，再將新的 out 內容複製到 Pages repository。工作流程接著以 github-actions[bot] 設定提交者資訊，建立訊息包含 tag 名稱的部署提交，最後把結果推送到 Pages repository 的 main。GitHub Pages 只需要服務這個已經產生好的靜態檔案，因此正式環境不需要安裝 Node.js，也不需要啟動應用程式伺服器。

這個流程把部署權限限制在 tag push 上。一般的 pull request 與 main push 只有讀取原始 repository 內容的權限，不能直接寫入正式 Pages repository；只有通過完整 build 並且明確建立版本 tag 時，才會使用 Pages publisher token 進行發佈。私有內容的讀取 token 與正式網站的發佈 token 也分開保存，避免同一組憑證同時擁有不必要的權限。

驗證與維護方式

本機驗證時，先使用 npm run lint 檢查 ESLint 規則，再使用 npm run type-check 執行 TypeScript 型別檢查，最後使用 npm run build 確認所有頁面、MDX 內容與靜態路由都能成功產出。正式的 GitHub Actions 目前執行 lint 與 build；type-check 是本機可使用的額外檢查，未來可以視團隊需求加入 CI，讓型別錯誤在更早階段被阻擋。

內容維護時，新增 Portfolio 或 Note 的主要工作是建立正確分類下的 Markdown 或 MDX 檔案，並填寫符合資料型別的 frontmatter。標題會影響文章目錄與錨點，category 與檔名則會影響網址，因此這些欄位應該視為內容的一部分，而不是單純的顯示文字。若文章引用圖片或其他靜態檔案，資源應放在 public 目錄並使用可以被靜態輸出解析的路徑。

後續演進

這個網站的架構刻意保留演進空間。當作品數量增加時，可以在既有的 frontmatter 上加入更精確的角色、技術領域或成果資料，然後由索引頁提供篩選與排序。當 Notes 需要更完整的搜尋功能時，也可以在建置階段根據現有文章產生搜尋索引，而不必立刻引入伺服器端資料庫。

未來若網站需要互動式表單、登入、即時資料或其他必須在伺服器執行的功能，靜態輸出策略就需要重新評估。目前的設計則刻意把動態需求排除在核心路徑之外，讓作品展示與技術文章保有穩定的網址、快速的載入速度與簡單的部署方式。這也是整個網站設計的主要取捨：先用檔案、型別與建置流程解決內容展示問題，再在確定需求出現時增加相應的服務。
