PowerShell-Based Test Execution

CI/CD 整合方案，透過 Python Wrapper 與 Robot Framework 重用 PowerShell 韌體驗證邏輯，避免重複實作。

01. 專案背景

原本的 Firmware Validation 流程由 NCP Firmware Validation Team 進行手動驗證，並將驗證流程撰寫成 PowerShell Script，在 Host PC 上執行。

隨著這些驗證情境需要導入 CI/CD，自動化測試框架採用 Robot Framework，而團隊既有的自動化實作主要以 Python 為主。

因此，原本的整合方式是將既有的 PowerShell Validation Flow 重新以 Python 實作，再整合至 CI/CD Test Framework。

這種方式雖然可以將驗證流程導入 CI/CD，但也造成相同的 Validation Logic 同時存在於 PowerShell 與 Python 中。當 Validation Flow 後續修改時，兩份 implementation 都需要同步維護。

因此，本專案的核心問題並不是「如何將 PowerShell 改寫成 Python」，而是：

如何讓既有的 PowerShell Validation Flow 直接被 CI/CD 使用，同時避免重新實作與維護相同的 Validation Logic。

02. 專案目標與系統架構

2.1 專案目標

本專案的目標，是將既有的 PowerShell Validation Flow 整合至 CI/CD Test Flow，使既有的 Validation Logic 可以被 Robot Framework 直接執行，而不需要重新以 Python 實作。

在系統設計上，我將 Python 與 PowerShell 的責任分開：

  • Python：負責 CI/CD Integration、Test Execution Control 與 Result Handling
  • PowerShell：保留既有的 Firmware Validation Logic

透過這樣的分工，讓既有 Validation Logic 可以被重複使用，同時降低後續維護時的 Logic Duplication。

2.2 Existing Automation Approach

原本導入 CI/CD 的方式，是將既有 PowerShell Validation Flow 重新實作為 Python，再交由 Robot Framework 執行。

這種架構雖然可以整合至 CI/CD，但 Python 與 PowerShell 之間會產生重複的 Validation Logic。

當原有 Validation Flow 發生修改時，除了更新 PowerShell Script，也需要同步修改 Python implementation，增加後續維護成本。

2.3 Proposed Architecture

為了解決 Validation Logic Duplication，我將 Python 定位為 PowerShell 與 CI/CD Framework 之間的 Integration Layer，而不是重新實作 Validation Logic。

Python Wrapper 負責 Test Flow、Script Execution、Parameter 傳遞、Result Handling 與 Error Handling；PowerShell 則維持原有的 Validation Logic。

在 CI/CD 執行時，Robot Framework 透過 Python Wrapper 啟動對應的 PowerShell Validation Flow。Python 負責控制測試執行與結果處理，而實際的 Validation Logic 仍由 PowerShell 執行。

因此，後續 Validation Flow 的修改可以直接發生在 PowerShell，而不需要同步維護另一份 Python implementation。

03. 我的設計與實作

3.1 PowerShell Wrapper & Integration Interface

為了讓既有的 PowerShell Validation Flow 能夠直接整合至 CI/CD Test Flow，我在 Python 中建立 PowerShell Wrapper，負責 PowerShell Script 的執行，以及 Python 與 PowerShell 之間的 Integration Interface。

由於不同的 PowerShell Validation Script 都需要透過相同的 Wrapper 執行，因此我先定義統一的 Script Interface，讓 Python 可以用一致的方式與不同 PowerShell Script 進行互動。

主要定義：

  • Script Execution
  • Input / Parameter
  • Return Value / Result
  • Error Handling
  • Log Handling

透過統一 Interface，Python 不需要理解每一個 Validation Script 的內部實作，只需要依照既定規格控制 Script 執行並處理結果。

3.2 Script Execution & Parameter Handling

PowerShell Script 由 Repository 進行管理。

在 CI/CD Pipeline 執行時，Python Wrapper 依照 Test Flow 指定需要執行的 Script，將 Script 取得並在 Host PC 上執行指定的 PowerShell Validation Flow。

因此，Python Wrapper 主要負責 Execution Control，而實際的 Validation Logic 則保留在 PowerShell Script 中。

既有的 Manual Validation Flow 中，PowerShell Script 會根據不同測試情境接收 Input Parameters，因此我也定義統一的 Parameter 傳遞方式，使 Python Wrapper 可以將 Test Flow 所需的參數傳入 PowerShell Script。

PowerShell Script 再依照定義好的 Interface 接收對應參數，執行指定的 Validation Flow。

這使不同 Validation Script 可以透過相同的方式接收測試條件，而 Wrapper 不需要針對每一個 Script 建立不同的 Parameter Handling。

3.3 Return Value & Error Handling

為了讓 Python Wrapper 能夠一致判斷不同 Validation Script 的執行結果，我定義統一的 Return Value。

Validation Result 與 Execution Error 需要能夠被 Wrapper 明確區分，例如：

  • True → Validation Pass
  • False → Validation Fail
  • Error → Script Execution Error

Python Wrapper 不需要理解各 Validation Script 的內部 Validation Logic，只需要根據統一的 Return Value 判斷執行結果，再將結果傳遞至 Robot Framework。

此外，我在 PowerShell Script 中建立統一的 Exception Handling 機制，透過 try/catch 捕捉執行過程中的 Exception。

當發生 Execution Error 時，PowerShell 依照定義好的格式回傳 Error Information，使 Python Wrapper 能夠識別 Script Execution Error，並將對應結果反映至 CI/CD Test Flow。

透過 Result 與 Error 的標準化，讓不同 Validation Script 可以使用一致的方式與 CI/CD Test Framework 進行整合。

3.4 Log Handling Strategy

除了 Validation Result 外，CI/CD 也需要保留完整的執行 Log，供測試完成後進行結果確認與 Debugging。

然而，由於 PowerShell 是透過遠端方式執行，執行過程中的 Log 並無法以完整且即時的方式呈現在 CI/CD Pipeline UI。

在 Multi-thread PowerShell Validation Flow 中，這項限制更加明顯。不同 Thread 的 Log 無法單純依賴遠端執行輸出，即時且完整地回傳至 Python。

針對這項限制，我評估實際的 CI/CD 使用情境後，決定不額外建立即時 Log Streaming 機制。

原因是這類 CI/CD Test Flow 的主要使用方式，是提交測試後等待執行完成，再查看最終 Test Result 與 Log。因此，即時更新 Pipeline UI 並不是必要需求。

基於這個使用情境，我保留既有的遠端執行模式，將 Execution Result 與 Log Storage 分開處理。

PowerShell 在 Host PC 上儲存完整的執行 Log，測試完成後再將 Log File 納入 CI/CD Artifact。

這個設計避免為了非必要的即時 UI 增加額外的 Communication 或 Streaming Mechanism，同時仍保留測試完成後所需的完整 Log。

3.5 Development Guideline & PowerShell Template

完成 PowerShell Wrapper 與 Integration Flow 後，我將實際驗證過的 Integration Interface、使用方式與技術限制整理成 Development Document，提供團隊後續開發與維護 PowerShell Validation Script 時參考。

除了文件化 Integration Rules 外，我也提供 Template PowerShell Script，將 Wrapper 所需的基本結構預先建立，讓開發團隊可以依循既定模式開發新的 Validation Script。

同時，針對 PowerShell Script 的管理定義：

  • Repository Location：統一 PowerShell Script 的存放位置
  • Script Version：每次 Script 修改時更新 Version
  • Integration Rules：新的 Validation Script 依循既定 Interface 開發

透過 Development Guideline 與 PowerShell Template，將實際驗證過的 Integration 方式與使用規範標準化，使後續新增或修改的 PowerShell Validation Script 可以依循相同規範納入 CI/CD。

04. 成果

本專案將既有的 PowerShell Validation Flow 直接整合至 CI/CD Test Flow，避免為了自動化而重新以 Python 實作相同的 Validation Logic。

透過 Python PowerShell Wrapper，Python 負責 Test Execution Control、Integration 與 Result Handling，而 PowerShell 持續作為 Validation Logic 的主要實作。因此，後續 Validation Flow 修改時，不需要同步維護另一份 Python implementation。

在 CI/CD 整合上，既有 PowerShell Validation Script 可以透過統一的 Integration Interface 被 Robot Framework 執行，並將 Validation Result 與 Execution Error 以標準化方式回傳至 Test Flow。

在 Log Handling 上，則根據實際 CI/CD 使用情境採用完成後取得 Artifact 的方式，保留完整測試 Log，同時避免為非必要的即時 Log Streaming 增加額外系統複雜度。

此外，透過 Development Guideline 與 PowerShell Template，將 Wrapper Interface、Script Structure 與管理規範標準化，使後續新的 Validation Script 可以依循相同模式開發與整合。

最終建立一套以 PowerShell 保留 Validation Logic、Python 負責 Integration 與 Execution、Robot Framework 負責 CI/CD Test Flow 的自動化測試架構。
