Automated iPhone Provisioning System

An iOS device automation framework that extends an Android-based provisioning platform with screen-state validation, workflow control, and error handling.

Mobile Device TestingiOSAutomation Framework

01. 專案背景

原有的 Mobile Device Provisioning Automation Framework 主要以 Android Device Automation 為基礎，已具備完整的自動化流程與執行架構。

Provisioning 流程包含 Device 設定、Profile 設定、App 安裝、帳號設定、UI 操作與設定結果確認等多項操作。

Android Device 可以透過既有的 Command / CLI-based Interface 執行裝置操作，因此原有 Automation Framework 能夠透過 Software Command 控制 Device。

當系統需要延伸支援 iOS Device 時，原有的 Android Automation 方式無法直接沿用。iOS 的操作方式與 Android 不同，因此需要建立另一套 Device Control 與狀態驗證機制。

本專案的核心工程問題是：

如何在既有 Automation Framework 的基礎上，加入 iOS Device Automation Capability，讓系統能夠透過裝置畫面判斷目前狀態，並根據狀態執行後續自動化操作？

因此，我主要負責 iOS Automation Framework 的設計與實作，建立 Device Input、Screen State Validation、Workflow Control 與 Error Handling 之間的整合能力，使既有 Automation Framework 能夠延伸支援 iOS Device。

02. 專案目標與系統架構

2.1 專案目標

本專案的主要目標，是將 iOS Device 納入既有 Automation Framework，建立可支援多裝置執行的 iOS Automation Capability。

主要目標包含：

  • 建立 iOS Device Input Control
  • 建立 iOS Screen State Validation
  • 將 Device 操作與畫面狀態整合
  • 支援 Multi-Device Automation
  • 建立 Retry 與 Error Handling 機制
  • 提供明確的 Error Information 與人工介入機制

核心設計並不是重新建立一套獨立的 iOS Automation Framework，而是將 iOS Device 的控制方式整合至既有 Automation Architecture。

2.2 System Architecture

由於 iOS 無法直接沿用原有 Android Command-based Automation，因此建立兩個主要能力：

Input Control

透過外部 Input Device 將 Automation Command 轉換為 Device 操作，例如 Click、Select、Text Input 與 UI Interaction。

Screen Validation

取得 iOS Device Screen，再由 Automation Framework 根據目前畫面進行 State Validation。

因此，完整的 Automation Flow 不再只是執行固定的 Input Action，而是：

Input Action → Screen State Validation → Workflow Decision → Next Action

Automation Framework 根據 Device 目前的畫面狀態確認操作是否完成，再決定是否進入下一個 Workflow Step。

此外，在 Multi-Device Automation 情境下，Framework 需要獨立管理每個 Device 的 Execution State、Workflow Progress、Screen State、Error State 與 Retry State。

03. 我的設計與實作

3.1 iOS Automation Layer

我的主要工作是建立既有 Automation Framework 的 iOS Support Layer。

我沒有另外建立一套獨立的 iOS Automation Framework，而是延伸既有 Framework 的 Device Abstraction，將 iOS 特有的 Device Control 與 Validation Logic 封裝在 iOS Automation Layer。

透過 Platform-specific Layer 將 Android 與 iOS 的 Device Control 差異隔離，使上層 Automation Workflow 可以維持一致，而不同 Platform 的實作則由各自的 Layer 負責。

這樣的架構讓 iOS 成為既有 Automation Framework 中的一個 Device Platform，而不是額外維護一套獨立系統。

3.2 Input Control

由於 iOS 無法直接使用原有 Android Command-based Device Control，因此使用外部 Input Device 模擬實體操作。

Automation Framework 將 Workflow 中的操作轉換為對應的 Input Action，再透過 Input Device 作用於 iOS UI。

支援的操作包含：

  • Click
  • Select
  • Text Input
  • UI Interaction

這讓 Automation Framework 可以透過與實體操作相近的方式控制 iOS Device，而不需要依賴原有 Android 的 Command Interface。

3.3 Screen State Validation

單純執行 Input Action 無法確認 Device 是否真的完成預期操作，因此我建立 Screen Validation 機制，將畫面狀態納入 Automation Workflow。

Automation Framework 取得 iOS Device Screen 後，分析目前畫面並進行 State Validation。

例如執行某個 UI 操作後，Framework 不直接假設操作成功，而是確認目前畫面是否已進入預期 State。

因此 Automation Workflow 從原本的：

執行操作

延伸為：

執行操作 → 確認畫面狀態 → 判斷結果 → 決定下一個 Workflow Step

透過這種方式，Device 的實際 UI State 成為 Automation Flow 的判斷依據。

3.4 Multi-Device Automation

由於系統需要同時執行多個 Device，因此每個 Device 都需要維持獨立的 Automation Context。

Framework 分別管理每個 Device 的：

  • Execution State
  • Workflow Progress
  • Screen State
  • Error State
  • Retry State

不同 Device 可以依照自己的 Workflow 狀態持續執行，不會因為單一 Device 發生異常而直接影響其他 Device 的執行。

因此，Device Control 與 Workflow State 必須從單一 Device 的操作邏輯中抽離，才能支援 Multi-Device Execution。

3.5 Retry 與 Error Handling

Production Automation 中，部分錯誤可能屬於偶發性問題，因此我建立 Retry 機制，避免單次異常直接導致 Workflow Fail。

當 Workflow Step 發生錯誤時，Framework 會依照既定的 Retry Policy 重新執行。

如果錯誤持續發生，則停止自動重試並將 Error Information 提供給 Operator。

這樣可以區分：

  • Transient Error：透過 Retry 嘗試恢復
  • Persistent Error：停止自動重試並交由 Operator 處理

因此，Error Handling 不只是單純判斷 Pass / Fail，而是讓 Automation Framework 能夠針對不同錯誤狀態採取不同處理方式。

3.6 Framework Integration

在 iOS Automation 的設計過程中，我主要考量的不是單獨讓 iPhone 能夠被控制，而是如何讓 iOS 成為既有 Automation Framework 中的一個 Device Platform。

因此，我將 iOS-specific implementation 與既有 Automation Workflow 分離，使上層 Workflow 不需要直接處理 iOS 的控制細節。

上層 Framework 負責 Automation Workflow，而 Platform Layer 負責對應 Device 的操作與狀態處理。

透過這樣的分層，使既有 Automation Framework 可以在維持原有架構的情況下，延伸支援不同 Device Platform。

04. 成果

本專案將原本以 Android 為主要支援對象的 Automation Framework 延伸至 iOS Device，建立完整的 iOS Provisioning Automation Capability。

在 iOS Device Control 上，透過 Input Control 執行 Device 操作；在操作結果確認上，則透過 Screen State Validation 將實際 UI 狀態納入 Workflow Decision。

同時，Framework 支援 Multi-Device Execution，並獨立管理各 Device 的 Workflow、Screen State、Error State 與 Retry State。

在 Production Automation 上，建立 Retry 與 Error Handling 機制，使系統能夠處理偶發性錯誤，並在持續性錯誤發生時提供明確的 Error Information 給 Operator。

最終，原有以 Android 為基礎的 Automation Framework，透過 iOS Automation Layer、Input Control、Screen State Validation、Multi-Device Execution 與 Error Handling，延伸成能夠支援不同 Device Platform 的 Automation Framework。

本專案的核心成果可以歸納為：

Android-based Automation → Multi-Platform Automation

Command-based Control → Input + Visual State Validation

Fixed Execution → State-based Workflow Control
