01. 專案背景

本專案為手機 Functional Test Automation，將原本由人工執行的手機上下料流程轉換為 Robot Automation。

在導入自動化之前，測試設備的操作主要由人工完成。操作人員需要將手機放入測試設備，等待 Functional Test 完成後，再將測試完成的手機取出。

隨著測試流程導入 Robot Automation，原本由人工負責的上下料工作改由機械手臂執行，並讓單一 Robot 同時服務多個 Test Stations。

因此，Robot 不再只是按照固定順序執行 Pick / Place Motion，而需要持續取得各測試站的狀態，並根據目前的設備狀態決定下一個操作。

本專案的核心工程問題因此從單純的 Robot Motion Control，延伸為 Communication、State Management、Control Flow 與 Robot Action 的整合。

我的主要負責範圍為 Robot 與 Test Station 之間的通訊、狀態管理與控制流程整合，以及驗證 Robot 端控制程式是否符合整體自動化流程的協作需求。

02. 專案目標與系統架構

2.1 專案目標

本專案的目標，是將原本由人工執行的手機上下料流程轉換為多站點 Robot Automation，使 Robot 能夠根據各測試設備的狀態，自動完成手機的放入、測試等待與取出。

系統需要整合 Robot Controller、Test Stations、Camera 與 Conveyor，並建立：

  • Robot Controller 與 Test Station Services 的通訊
  • 多個 Test Station 的狀態管理
  • Test Status 與 Robot Motion 的同步
  • Camera 提供的 DUT 尺寸資訊
  • 根據 DUT Size 調整 Gripping Parameters
  • Input / Output Conveyor 的設備協作

2.2 System Architecture

整體系統以 Robot Controller 作為設備協調層，負責整合 Camera、Test Station Services、Robot Arm 與 Conveyor 的狀態及控制流程。

各 Test Station 透過對應的 Service 提供設備狀態，Robot Controller 統一取得並管理這些資訊，再依據目前的 System State 決定 Robot 的下一個操作。

整體 Automation Flow 由 Input Conveyor 將 DUT 送入系統，經由 Camera 取得必要資訊後，由 Robot Controller 根據 Test Station 狀態安排後續操作。Robot 將 DUT 放入可執行測試的 Station，等待 Functional Test 完成後，再由 Robot 取出並送往 Output Conveyor。

透過這樣的架構，將 設備通訊、狀態管理、控制邏輯與 Robot Motion 分層處理，使 Robot Controller 成為多個設備之間的協調中心。

03. 我的設計與實作

3.1 Robot 與 Test Station Communication

我的主要負責範圍之一，是建立 Robot Controller 與多個 Test Station Service 之間的通訊與整合。

每個 Test Station 由對應的 Service 提供設備狀態，Robot Controller 透過一致的 Communication Interface 取得資訊，而不需要直接處理各 Test Station 的內部實作。

透過 Test Station Service 將各 Test Station 的實作細節與 Robot Control Logic 分離，使 Robot Controller 可以透過一致的 Interface 管理多個測試站

3.2 Multi-Station State Management

由於單一 Robot 同時服務多個 Test Stations，各站可能同時處於不同的測試狀態，因此 Robot Controller 需要持續取得並管理各 Test Station 的 State。

Controller 根據目前的 Station State 判斷哪些測試站可以進行下一步操作，再將 Control Decision 交給 Robot Control Flow。

因此，Robot 的下一個動作並非依賴固定的 Station 順序，而是根據當下的 System State 決定。

這種 State-based Control 讓同一套 Robot Control Flow 能夠應對多個測試站不同步的測試狀態。

3.3 Robot / Test Synchronization

Robot 將 DUT 放入 Test Station 後，需要等待 Functional Test 完成。

因此，控制流程不是使用固定等待時間判斷測試是否結束，而是透過 Test Station Service 回報的狀態進行同步。

Robot Controller 根據 Test Status 判斷測試是否完成，確認符合後續條件後，再觸發 Robot Retrieve。

透過這種方式，將 Test Station 的實際測試狀態與 Robot Motion 串接，確保 Robot Action 與 Functional Test Flow 保持同步。

3.4 Camera Integration & DUT Handling

Input Conveyor 上的 Camera 提供 DUT 尺寸資訊。

我將 Camera 資訊整合至 Robot Control Flow，使 Controller 能夠根據 DUT Size 調整 Robot 的 Gripping Parameters。

因此，Robot 在執行 DUT Handling 時，不需要完全依賴固定的 Gripping Configuration，而可以根據實際取得的 DUT Information 使用對應的抓取設定。

這項資訊也被納入整體 Robot Control Flow，與後續 Pick、Move以及Place 操作整合。

3.5 Multi-Station Control Flow

多站點環境下，Robot Controller 需要將不同 Test Stations 的狀態整合為單一 Control Decision。

控制流程會根據 Station Availability、Test Status、DUT Flow 與 Robot 狀態判斷下一個操作，再由 Robot Control Flow 執行對應的 Pick / Place Motion。

因此，Robot 的 Motion Control 並不是獨立運作，而是由上層 State Management 與 Control Flow 根據實際設備狀態觸發。

這使單一 Robot 可以在多個 Test Stations 之間進行協作，而不需要將整個流程限制為固定的執行順序。

3.6 Robot Control Program Validation

除了 Communication 與 Control Flow Integration，我也負責驗證 Robot 端控制程式，確認 Robot Control Program 能夠與 Test Station Service、Test Flow 以及整體設備狀態正確協作。

驗證過程不只確認單次 Pick / Place Motion 是否正常，也需要確認不同設備狀態下的 Robot Action 是否符合預期。

當發現 Integration Issue 時，我會從 Communication、State Transition、Control Logic 與 Robot Behavior 等層面進行分析，確認問題發生的位置，再進行 Integration Logic 修正或提供明確的問題資訊進行後續處理。

04. 成果

本專案完成由人工手機上下料轉換為 Robot 自動上下料的多站點 Functional Test Automation Flow。

透過 Robot Controller 整合 Test Station Communication、State Management、Control Flow 與 Robot Motion，使單一 Robot 能夠根據多個 Test Stations 的實際狀態進行自動化操作。

同時整合 Camera 提供的 DUT Size Information，讓 Robot 可以依據不同 DUT 條件調整 Gripping Parameters，並完成 Input Conveyor、Functional Test Stations 與 Output Conveyor 之間的自動化流程串接。

最終將原本的人工操作流程轉換為以 State-based Control 為核心的 Multi-Station Automation，使 Robot 不只是執行固定 Motion，而是能夠依據設備狀態進行協調與控制。
